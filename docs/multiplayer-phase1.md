# .15 多人第一阶段：数据通路与原版只读副本

2026-10-11。以 `.14`（`bad9ece`）为开发基线，代码仅在 `multiInstanceTest`。本阶段完成内部订阅及原版战斗副本，尚未开放多人 F8 导航、个人选择页和操控权限。`.12` 及已验收功能未重新测试。

## 已落实的通路

来源玩家原版 `CombatReplayWriter` → 同房间可靠消息 `RmpMirrorPacket` → 原版房主核验发送者并定向路由 → 观看者本机认证管道 → 独立进程 `NetReplayGameService` → 原版 `NRun`、战斗及手牌控件。

副本不加入原版房间、不占玩家槽位、不连接 Steam、不保存对局。游戏操作仍由原版房主的 `ActionQueueSynchronizer` 排序；来源客户端不能替房主重新决定动作。多人回放保留原版 `Replay` 类型，不沿用单人副本转换为 `Singleplayer` 的补丁。

战斗首次订阅发送原版不可变初始检查点及已有事件；后续只发送新增的 `GameAction`、`HookAction`、`ResumeAction`、`PlayerChoice`。每次原版战斗检查点更新采用新 generation。实现没有重置或修改来源的原版回放记录器，也没有传输画面。

消息包含协议、游戏/Mod/模型序列化版本、来源与目标、订阅随机标记、来源会话、generation 和连续事件范围。房主拒绝伪造来源；观看者只接收房主路由给自己的消息，旧订阅、旧 generation 及不连续事件不能进入副本。可靠消息按 32 KiB 分片，上限 32 MiB，重组数量和等待时间有界。网络消息不携带本机管道密钥。

界面元数据与空增量继续更新来源状态，但空增量不进入副本加载队列，避免慢加载时积压。校验需要副本完成加载、双方静止、事件数和完整状态 hash 一致。多人 hash 排除计时、发现记录、地图绘图及传输平台标记；原版 Replay 的平台为 None，不能把它与 Steam 来源的平台差异误判为对局变化。单人 hash 的处理没有改变。

## 原版多人逻辑的差异及数据缺口

| 数据/机制 | 第一阶段结论 | 后续窗口需要补充 |
| --- | --- | --- |
| 全队角色、牌堆、生命、能量、随机状态 | 原版检查点及原生事件可重建，双来源状态校验通过 | 加入可见窗口及来源切换 |
| 并发出牌 | 必须按原版房主排序，不按各窗口自己的输入顺序执行 | 操控请求仍走原版权威链路 |
| Hook、等待选择、恢复 | 四类事件全部要消费；只同步出牌会漏掉选择与恢复 | 以原版玩家和 choice/action ID 绑定选择 |
| 个人手牌选择 | 来源能发送手牌模式；Replay 会等待原版 choice 结果，不能直接展示玩家选择器 | 捕获候选牌身份、筛选规则、最少/最多数量、已选项及确认/取消条件 |
| 弹出选择页 | 当前可采集原版 overlay 类型及可见卡牌序列化信息 | 这些数据不足以恢复所有 selector 的行为和操控合法性 |
| 地图、事件、奖励、商店、火堆、宝箱 | 原版战斗回放不是跨房间日志，本阶段未接通这些多人场景 | 另外设计公共房间状态和每位玩家私人页面协议，不能照搬单人操作日志 |
| 权限与重连 | 实现内部订阅身份校验及取消；没有远程操控权限 | 授权、撤回、断线、来源切换和错误恢复的公开流程 |

因此，现有数据足以支持本阶段只读战斗状态同步；不足以直接完成所有多人页面和操控。下一阶段应先补个人 UI 数据契约，再开放多人窗口。

## 立绘与身份

原版 `NCombatRoom.PositionPlayersAndPets` 以 `LocalContext.IsMe` 决定最前方角色位置及节点绘制顺序。因此副本在创建原版 Replay 服务和同步器之前，将本地观察身份绑定到所选来源：`.111` 使用原版来源参数，`.107` 在 Replay 服务构造时设置 NetId。

不交换 `RunState.Players` 的槽位，不重排队伍或同步器编号。本体依旧以自己的 NetId 展示；副本以所选玩家 NetId 展示。专项测试实际检查两个原版角色节点的位置和兄弟节点绘制顺序，双方本体与副本均符合要求。测试为 headless，未做可见窗口截图验收。
