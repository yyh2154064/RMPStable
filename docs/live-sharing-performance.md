# 实况观战性能与布局修正记录

版本 `0.3.9-liveSharing.4`，分支 `liveSharingTest`，记录日期 2026-10-06。

## 问题与本轮处理

原型每 250 ms 在游戏主线程完整遍历场景、生成快照、JSON 往返，再更新显示。周期性工作集中在一个帧，容易让原游戏和观战动画同时停顿。地图的标签/卡牌查找会遍历大量节点；即使最终只找到几个标签，查找本身也有成本。只有渲染端保留节点，仍不足以解决采集阶段的长帧。

本轮实施：

- 将完整采集拆为可跨帧推进的节点/卡牌读取，以每帧 2 ms 软预算调度。文字、可见卡牌查找和图像遍历均可让出当前帧。所有 Godot 和游戏模型读取仍在主线程，不在后台线程访问引擎对象。
- 完成后发布不含游戏对象的快照，正常本地模式取消 JSON 往返。JSON 仅保留为开发验证入口。
- 快照按业务域维护版本，并精确比较全部 DTO 字段。未变化域复用上一份数据，减少重复更新。
- 利用牌组和卡牌事件失效缓存；隐藏牌组短时复用，主动浏览时刷新。轻量状态通知配合自适应轮询，覆盖未订阅的显示变化。
- 缓存本地资源路径，每次采集缓存同一材质实例的参数；不同实例独立采样，观战材质独立创建，保持颜色与原游戏一致。
- 保留状态栏、血条、意图、标签、地图和生物视觉节点，增量修改文字、位置、纹理、颜色、着色器参数；手牌仅位置变化时复用卡面。
- 牌组只实例化可见行与邻近缓冲行，完整 DTO 仍支持排序与上一张/下一张详情。200 张牌组测试的卡面实例少于 40 个。
- 地图笔迹单独每 50 ms 检查，线段不变时不重绘透明画布；不等待完整地图采集完成。
- 页面/房间/视口切换取消旧采集；跨帧图像层级沿用已经捕获的父变换。关闭时停止工作并解绑牌组和卡牌事件。

内部视口仍为 **1920×1080**，默认弹框宽度仍为最初内嵌版的 **3/5**。没有采用降分辨率。实况置于独立裁剪区域，按 16:9 充满区域，左右和底部内边距均为 3 个逻辑像素；默认标题区域由 44 缩至 40 个逻辑像素，背景直接衔接画面。拖动和缩放共用一次布局计算，不产生额外黑边、错位或溢出。敌人攻击数字的原版位置保持不变。

标题改为来源选择栏，每页三个玩家框，复用原版奖励框和卡牌详情箭头。未选中框采用深蓝底色及更深的外边框；选中框恢复原版搜刮金币奖励框的蓝色，不增加黄色线。默认框高 26 像素、宽度最多 150 像素，保留上下间隔与至少 96 像素拖动空白。右上角使用原版叉形纹理加红色着色。手动调整窗口宽度时，整个导航栏统一缩放，栏高与红叉右上角位置一起重新计算，红叉在按钮区域内裁剪。当前测试版提供本人和四个明确标注的模拟来源，五项都显示同一份本机状态；没有接入多人传输。

## 测量方法

使用本机 RTX 2060、游戏 v0.111.0、OpenGL compatibility、同一隔离运行环境和测试存档。对比上一版 `.3` 和本版 `.4` 的实际双版本安装包，均保留 1920×1080 实况视口。原游戏前台上限为 60 FPS，但采样没有锁定主窗口焦点，后台限帧仍可能生效；因此帧时间是本次运行记录，不能将差异全部归因于代码优化。最终包通过 213 项自动检查；v0.107.1 和 v0.111.0 实现以及引导 DLL 均为 0 警告、0 错误。

`tests/LiveSharingSmoke` 在商店、战斗、牌组、地图、奖励与先古之民流程中验证只读性、原版样式和生命周期。性能窗口内不截屏。正常运行记录 180 帧，不手动触发采集；同步压力测试另外记录 60 次完整采集，每次故意在一个帧内完成。P95/P99 为样本的第 95/99 百分位，数值越低表示长帧更少。

## 正常运行结果

| 场景与指标 | 上一版 `.3` | 本版 `.4` |
|---|---:|---:|
| 地图帧时间 P95 | 77.23 ms | 35.34 ms |
| 地图帧时间 P99 | 92.07 ms | 37.34 ms |
| 地图超过 33 ms 的帧数 / 180 | 31 | 20 |
| 地图超过 50 ms 的帧数 / 180 | 17 | 0 |
| 战斗帧时间 P95 | 36.80 ms | 30.85 ms |
| 战斗帧时间 P99 | 55.95 ms | 34.63 ms |
| 战斗超过 50 ms 的帧数 / 180 | 4 | 0 |

新版地图采集片段 P95 为 2.67 ms，纯采集 P95 为 2.12 ms，显示更新 P95 为 0.55 ms；最后一份地图采集分 3 帧完成，累计 CPU 时间约 5.75 ms。战斗纯采集 P95 为 2.02 ms。新版两个正常采样窗口末的引擎 FPS 均为 60；它是窗口末的读数，不是帧时间均值。待机动画保持连续运行，不以这些状态采集频率播放。

2 ms 是软预算：一次原版方法、引擎调用、垃圾回收或最终显示更新不可在内部中断。地图采集片段 P99 仍出现约 22.09 ms，因此不能声称所有片段都限制在 2 ms 或卡顿完全消失。

## 剩余边界

- 50–250 ms 是完整采集完成后的轮询等待，不包含采集所需的多个帧；状态通知可以提前刷新。不能直接解释成固定 20 Hz 或 50 ms 的端到端延迟。
- 首次场景/卡面加载、复杂卡牌描述生成、长地图笔迹及最终页面创建仍可能出现长帧。下一步应依据实际长帧记录进一步区分引擎调用、GC、CPU 与 GPU 成本，不靠降低画质掩盖问题。
- 跨帧读取并非游戏状态的原子事务。页面切换会取消，已完成快照不会被后续采集修改；同页快速变化仍可能在相邻采样点出现短暂差异。
- 当前资源通过路径复用本地文件，没有网络传输。多人协议还需要静态定义、稳定实体标识、增量状态、排序/恢复与资源版本匹配，本轮未加入多人通信。
- 实际图形运行验证为 v0.111.0；v0.107.1 只验证构建。隔离游戏退出仍有引擎资源日志，尚无长期原版对照，不将短时测试解释为已证明长期无资源问题。

开发输出为 `.tools/live-sharing/results-optimized` 与 `results-perf-before` 下的 `*-live-performance.json`、`map-performance.json`，以及原版/实况/嵌入截图；它们不随安装包分发。
