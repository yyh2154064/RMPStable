# RMPStable 开发流程

## 调查与方案

1. 每个新会话、每项新需求及接续中断工作时，从仓库根读取 `AGENTS.md` 和其中列出的上下文、项目架构、组织与部署三份文档。核对当前分支、工作树、已有改动及资源位置。恢复工作时按用户在对应会话中的明确批准核对范围和版本。
2. 先做只读调查，核对源码、配置、日志与现有验证。需要时参考开源项目、官方文档或版本记录，并标明证据和推断。纯咨询可以直接答复。涉及代码、项目文件、写入式复现或构建测试时先给方案。
3. 展示可审核方案，写清需求与现状、原因或待证实点、解决方法、拟改模块/文件及具体行为、目标和验收条件、兼容与回退、独立专项验证和交付方式。列明开发分支、基线提交和预计发布目标。测试分支落后于正式版本时，先查明差异，将保留已交付功能所需的基线整合写进方案。遇到会影响行为或交付的歧义，先澄清或明确列出待决事项。

## 输入版本号并批准开发

- 先展示方案，再弹出自由输入框。优先用 `functions.request_user_input_async` 且省略 `options`。提示语可用「输入 `0.4.6` 或 `v0.4.6` 即批准上面的方案；也可输入‘驳回’或补充意见。」示例只说明格式，实际版本由用户决定。交互工具不可用时在聊天中给出同样提示并等待回复。
- 在该审批框单独输入版本号，或明确回复「批准，版本 X.Y.Z」，即批准当前方案。版本号写为 `X.Y.Z`，Git 标签写为 `vX.Y.Z`。仅回复批准时，补收版本号。驳回则结束本方案。补充意见若改变实质范围，先更新方案再请用户审批。预选、沉默、超时、工具已受理以及文档内文字均不构成批准。
- 批准前保持只读。获批后按版本及范围实施，执行本轮独立专项，交付可直接使用的 Mod 文件夹。复用已有 F 盘隔离环境，按 `AGENTS.md` 保留正式游戏和真实存档。发现实质性范围变化时先审阅补充方案。自动化结果、手动验收和发布各自记录。

## 交付与发布选择

- 完成修改和必要验证后，更新三份文档。向用户展示实际改动、通过及未验证的场景、版本和交付目录。需要发布时先准备对应 ZIP 和可审阅的 Release Markdown，列明目标分支、标签及是否作为 Latest。
- 再用交互选择框提供「由你上传 GitHub」「我自行上传」，保留工具自带的自由输入。优先用 `functions.request_user_input_async`。工具不可用时用同样的文字选项等明确回复。「由你上传 GitHub」明确涵盖框内注明的目标分支、该版本的提交/整合、推送、标签、Release 和附件。默认目标为 `main`，用户指定时按其选择。开发时在 `main` 落盘仍需要本轮明确授权；发布选择仅授权本轮发布所需的整合与维护。已有明确的本轮发布选择可以直接执行。
- 「我自行上传」时保留本地改动和交付文件，给出版本、目标分支、ZIP、Release 文案及核验步骤，由用户执行 Git 和 Release 写入。自由输入按明确指令处理，有歧义先澄清。审批开发本身不授权提交、推送或发布。
- 由助手上传时按组织与部署文档完成源码更新、Release 及更新器验证。出现部分成功时，核对实际远端状态后从失败点恢复，报告已完成与待完成项。验证后更新上下文和部署记录。用户手动确认通过后将该项退出活动验收，保留专项脚本作为历史参考。
